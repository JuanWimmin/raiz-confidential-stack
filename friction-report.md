## [2026-08-03 00:30] — [CT] — SDK CircuitProver silently proves single-threaded: bb.js UltraHonkBackend defaults to { threads: 1 } and the SDK never overrides it
- Context: building scripts/prover-bench (standalone proving benchmark for the Session 1 spike). Read the vendor prover to replicate its exact call sequence: `packages/sdk/src/proving/prover.ts:74` constructs `new Backend(this.#bytecode)` with NO backendOptions. In `@aztec/bb.js@0.87.0` the constructor is `constructor(acirBytecode, backendOptions = { threads: 1 }, ...)` (dest/node/barretenberg/backend.js:25 and identically in dest/browser/index.js), and `Barretenberg.new({threads: 1})` feeds `fetchModuleAndThreads(1, ...)` -> `Math.min(1, availableThreads, 32)` = 1 thread. The multithread-friendly default (`desiredThreads = 32`) only applies when `options.threads` is undefined, i.e. when the caller passes `{}` — never when the second argument is omitted entirely.
- Verbatim error: (none — silent performance trap; proving succeeds on 1 thread)
- Version/commit: stellar-confidential-token-demo @ ac67499; @aztec/bb.js 0.87.0; @noir-lang/noir_js 1.0.0-beta.9
- Expected: the demo app's whole COOP/COEP + vendored-worker setup exists to enable SharedArrayBuffer multithreading, so CircuitProver proofs should use min(hardwareConcurrency, 32) threads when crossOriginIsolated. Observed: every CircuitProver proof (browser demo AND the SDK's own test/prove.mjs) runs on exactly 1 wasm thread regardless of isolation. Measured on this machine (Node v25.8.1, 22 CPUs, warm CRS): register 2735 ms / withdraw 5079 ms / transfer 5179 ms via CircuitProver, vs 1413 / 1741 / 1816 ms for the identical witness with an explicit `{ threads: 22 }` backend — a ~2-3x free speedup the demo leaves on the table.
- Workaround: prover-bench constructs its own `UltraHonkBackend(bytecode, { threads: crossOriginIsolated ? Math.min(navigator.hardwareConcurrency, 32) : 1 })` instead of going through CircuitProver in the browser. Our wallet's proving layer must do the same (or pass `{}`). Issue-draft candidate for OpenZeppelin's demo repo.

## [2026-08-03 18:05] — [RPC] — the getEvents retention floor moves while you use it: a `startLedger` read from `getHealth` seconds earlier is rejected with -32600
- Context: implementing per-contract historical backfill in /raiz-memory (a fresh index must reach back into the RPC's retention window instead of starting at the chain head). To start a contract's first scan as far back as possible we read the floor structurally — `POST https://soroban-testnet.stellar.org {"method":"getHealth"}` → `{"status":"healthy","latestLedger":3953872,"latestLedgerCloseTime":"1785789293","oldestLedger":3832913,"oldestLedgerCloseTime":"1785183187","ledgerRetentionWindow":120960}` — and pass `oldestLedger` as `startLedger` to `getEvents`.
- Verbatim error: `{"jsonrpc":"2.0","id":1,"error":{"code":-32600,"message":"startLedger must be within the ledger range: 3832943 - 3953902"}}` — returned for `startLedger: 3832922`, a value the SAME node had reported as its `oldestLedger` about 90 seconds earlier. Observed sequence within a few minutes: floor 3832913 → 3832922 (read, then used) → **rejected, range now starts 3832943** → 3832944.
- Version/commit: soroban-testnet.stellar.org, protocol 27, latestLedger ~3953900; raiz-memory @ this repo.
- Expected vs. observed: expected the advertised `oldestLedger` to be usable as a `startLedger` for at least the round trip that follows it. Observed the floor advances one ledger per ledger close (~5 s), so *any* "start as far back as possible" client races it — and the failure is a hard rejection of the whole call, not a partial result or a silent clamp. The window is a moving target on both ends, which makes "grab everything still available" strictly harder than it looks: there is no `startLedger: "oldest"` sentinel in the API.
- Workaround: read the floor from `getHealth` (structured field, no prose parsing) but treat it as advisory — on a -32600 rejection, parse `(oldest, latest)` back out of the error message, re-clamp `startLedger` to the new floor and retry, up to 3 times per tick (`rpc::parse_ledger_range_error` + the retry in `ingest::tick`). The error text is the only machine-readable place the *current* range appears at the moment of failure, so it cannot be ignored even though its wording is not part of any contract. Suggestion for the RPC: accept a sentinel (`startLedger: 0` or `"oldest"`) meaning "the oldest you still have", which would remove the race entirely for every archiving client — Nethermind's `tools/bootnode` and any getEvents-compatible indexer hit exactly this.
